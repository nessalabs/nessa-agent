## Boundaries and relationships checked

- **Composition and current authority.** Read the conflict-resolved `product/state.rs`, changes to `product/socket.rs`, `composition/local_auth.rs`, root composition and the GitHub/vault/relay composition modules against both HEAD and main. One composed vault is passed to GitHub, inbox key storage and Boat settings. Main's tunnel routes are additive; they do not replace the vault routes or skip the authenticated product dispatch/Cedar admission. The `ConnectionVault` owner still belongs to the socket loop, closes before response/subscription draining, and request clones retain only a non-owning lease.
- **Session owner, generation and publication.** Walked `nessa-vault` lifecycle and GitHub `connections.rs`: close marks the lease inactive before clearing its key; explicit lock increments the generation and clears under one mutex. Secret reads/writes/deletes check a live lease and captured generation. GitHub cache/attempt/save projections carry their admitted generation; publication rechecks it, while same-generation mutations serialize IO/publication through their own gate. A new generation does not wait on departed provider IO. The Saving phase exposes Connecting with no token until both audit and storage receipts; stale retirement does not steal its original terminal operation. Checked queued disconnect, old restore/save/delete and late-provider failure source paths against existing barrier-based regression cases in `tests/github/mod.rs`, `token_vault.rs` and vault lifecycle tests.
- **Migration source versus encrypted receipt.** Inspected `LegacyGithubMigration`, `verify_and_retire` and `GithubTokenVault`. Source locks span capture, destination verification and retirement. A required encrypted inbox key cannot be silently minted if its old key is absent. Conflicting legacy/private-file versus protected values refuse and preserve the source. `GithubTokenVault` reads bounded private JSON only for one-time upgrade, verifies matching encrypted readback before removing it, and removes migration input before protected delete to prevent resurrection. Normal post-marker operation does not require OS lookup. Scoped store calls fence stale writes/deletes from later unlocks.
- **At-rest truth and cost bounds.** Independently read `EncryptedFileVault` and SQLCipher encryption: fixed-profile Argon2id, XChaCha20-Poly1305 framing/authentication, fresh entropy, bounded input/file/entries and private lock/temp/atomic publication with verification. SQLCipher key loading refuses missing keys for existing encrypted bytes, and plaintext upgrade verifies a private encrypted replacement; decrypt failure preserves the source. The inbox acquires a key per operation instead of keeping a process-global SQLCipher connection. Already-admitted work may finish after close; this is distinct from new admission and does not establish forensic erasure.
- **Per-user event selection and offline receipts.** Read live-events application, connected store, credentials, SQLite selection/commit and follower/catch-up. The application checks the current user after repository discovery; selection and deletion evidence share one transaction. Binding generations and exact cursors are checked in the same commit transaction as insertion, so a removed selection cannot be revived by a late page. Store operations are keyed by user/repository/generation; no cloud event dispatches an agent turn. Watch subscription occurs between two durable catch-up passes; notifications carry hints only. Lock removes follower admission; permission/identity/gap/rate-limit failures back off.
- **Cloud authority and Free-stage boundaries.** Read Worker composition, signed ingress/D1 adapters, read application, GitHub identity adapter, Cedar policy, per-user budget SQL and installation/repository usage triggers, wake tickets/rooms and compiled deployment configuration. Payload reads require freshly verified GitHub user/repository facts, expected-user equality and Cedar approval, with audit before page delivery. Private repositories require the selected active App's permissions unless a verified `repo` OAuth scope applies. Auth/response bodies and storage capacity are bounded; native edge limits precede provider work; verified-user counters and signed-installation storage quotas are atomic. Hibernating sockets contain expiry/user metadata and no payload/token. Non-dev stages remain null with no fallback; deployment tests refuse missing stage resources or reused App identities. D1 uses provider-managed encryption at rest, not application E2EE; Worker plaintext visibility remains correctly stated in ADR 1132 and README.
- **Boat and native app consumers.** Read `VaultSettings`, save/clear application admission, composition and provider allocation boundary. Boat validation captures a vault generation; its delayed save/clear uses `write_in`/`delete_in`, not a second credential file/keychain. Read native vault anonymous-pipe process/command/deadline implementation: no passphrase in argv/env; bounded input/output; overlap refusal; request-specific timeout invalidates/kills the matching child; only status may retry after uncertain delivery. App closure is independent of a webview reload. This does not recall credentials already handed to admitted agents/providers or promise active VM termination when locking.
